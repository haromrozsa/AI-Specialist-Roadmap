# ML Fundamentals – Support Vector Machines & Kernels

# Session Summary: The Margin Is The Model, And Gamma Is The Knob That Overfits

One script, seven figures. An SVM is the first model in this repository whose
*geometry* is the whole idea, so everything here is built on 2-D synthetic data
where the decision boundary can actually be drawn. A boundary you cannot see
teaches nothing about a margin.

That is a deliberate departure from the previous two tasks
(`trees_and_boosting/`, `shap_explainability/`), which both reused the Titanic
split for comparability. Titanic has seven features after encoding; its boundary
cannot be plotted, and a bare accuracy number would not have shown what an SVM
is.

The gap this closes: zero hits for `SVC`, `SVR` or `svm` anywhere in the
repository before this. Linear and logistic regression, trees, forests, boosting
and KMeans were all covered; the other classical model everyone asks about in an
interview was not.

## Running

```bash
cd svm_kernels
python SVMKernels.py
```

Requires `scikit-learn`, `numpy` and `matplotlib`. No dataset download — both
datasets are generated by `sklearn.datasets` — so this one runs offline.

Run headless with `MPLBACKEND=Agg`; every figure is saved before `plt.show()`, so
a headless run produces the identical artifacts.

## What I Did During the Session

- **Made the kernel trick literal.** `make_circles` with one class ringed around
  the other, then lifted by hand into `φ(x) = (x₁, x₂, x₁² + x₂²)` so a flat
  plane separates it, then fitted an RBF SVC to show it finds the same circular
  boundary without ever building that third dimension
- **Drew the margin.** Contoured the raw `decision_function` at −1, 0 and +1
  rather than only at the class flip, and circled the support vectors, so "the
  points that hold up the boundary" is a picture rather than a phrase
- **Refit on the support vectors alone** and compared predictions point by point,
  so the defining property of the model is a measurement and not a claim
- **Swept `C`** over six orders of magnitude, tracking the support-vector count
  alongside accuracy — the count is the most direct read-out of the
  margin/violation trade-off
- **Swept `gamma`** over six orders of magnitude, up to the point where the model
  draws private islands around individual training points
- **Searched both jointly** with 5-fold `GridSearchCV` on the training split only,
  and plotted the CV surface as a heatmap
- **Broke the feature scale on purpose** (one feature × 1000) to measure what the
  scaler is actually buying

Everything is wrapped in a `Pipeline(StandardScaler, SVC)`, so the scaler is
fitted on training folds only and the cross-validation stays honest.

## Results

All numbers below are from the committed run: `make_moons`, n=300, noise=0.25,
70/30 stratified split, `random_state=42`.

### The kernel trick (`01_kernel_trick.png`)

| kernel | training accuracy on `make_circles` |
|---|---|
| linear | 0.6167 |
| RBF | **1.0000** |

Classes are balanced 150/150, so the linear kernel is barely above chance. It is
not a weak model — it is the *correct* answer to an impossible question. No line
separates a ring from its centre. The middle panel shows why the RBF kernel can:
in the lifted space, the red core sits below a flat green plane and the blue ring
above it.

### Linear vs RBF, margin drawn (`02_linear_vs_rbf_margin.png`)

| kernel | train | test | support vectors |
|---|---|---|---|
| linear | 0.8714 | 0.8444 | 66 / 210 |
| RBF | 0.9095 | **0.8667** | 69 / 210 |

The moons are *almost* linearly separable at this noise level, so the linear
kernel is only two points behind. The interesting part is the picture, not the
gap: the dashed margin band on the RBF panel bends, and every circled point either
sits inside that band or on the wrong side of it.

The defining property is checked rather than asserted. Throw away the 141
uncircled points, refit on nothing but the 69 support vectors, and:

```
refit on the 69 support vectors alone: 1.0000 of test predictions identical
max |decision_function| difference over the test set: 9.94e-04
```

Not "similar" — identical, with a residual at solver-tolerance scale. Two thirds
of the training data contributed nothing to the fitted model.

One trap found while measuring this: with `gamma='scale'` the agreement was only
0.9556. `'scale'` is `1/(n_features · X.var())`, so refitting on a subset silently
recomputes gamma and changes the kernel. Pinning gamma to a number is what makes
the comparison test the claim instead of testing the heuristic.

### C: the price of a margin violation (`03_C_sweep.png`, `04_C_vs_support_vectors.png`)

| C | train | test | support vectors |
|---|---|---|---|
| 0.01 | 0.8810 | 0.8556 | **210 / 210** |
| 0.1 | 0.8857 | 0.8667 | 117 / 210 |
| 1 | 0.9095 | 0.8667 | 69 / 210 |
| 10 | 0.9095 | 0.9000 | 46 / 210 |
| 100 | 0.9286 | 0.9111 | 39 / 210 |
| 1000 | 0.9429 | 0.9111 | 37 / 210 |

At C=0.01 *every single training point* is a support vector. That is the clearest
statement of what small C does: violations are nearly free, so the margin widens
until it swallows the entire dataset. As C rises the margin narrows and the model
ends up resting on 37 points out of 210.

### gamma: how far one point's influence reaches (`05_gamma_sweep.png`)

| gamma | train | test |
|---|---|---|
| 0.01 | 0.8619 | 0.8222 |
| 0.1 | 0.8667 | 0.8444 |
| 1 | 0.9238 | 0.9000 |
| 10 | 0.9667 | **0.9222** |
| 100 | 0.9857 | 0.9111 |
| 1000 | **1.0000** | 0.6556 |

The RBF kernel is `exp(-gamma · ‖x − x′‖²)`, so gamma is the inverse width of the
bell. At gamma=0.01 every point influences the boundary from across the plane and
the result is nearly a straight line. At gamma=1000 influence dies within a tiny
radius and the model degenerates into blue islands drawn around individual
training points: perfect 1.0000 on train, 0.6556 on test. This is the rare case
where overfitting is not inferred from a metric gap — you can see it in the panel.

### C and gamma together (`06_C_gamma_heatmap.png`)

5-fold CV on the training split, best `C=1, gamma=1` at CV 0.9143, giving test
**0.9000**. The heatmap shows a broad plateau around 0.87–0.91 and a cliff on the
right-hand column: at gamma=1000 no value of C rescues the model (0.53–0.58).

## What Surprised Me

**Large C did not overfit here.** The textbook line is that large C narrows the
margin until the model overfits, and test accuracy should fall off. It never did —
test accuracy rose monotonically from 0.8556 at C=0.01 to 0.9111 at C=1000 and
stayed there. The reason is visible in `03_C_sweep.png`: with `gamma='scale'`
(≈0.5 on two standardised features) the kernel is wide, so even at C=1000 the
boundary it can draw is still smooth. It cannot carve islands, however hard C
pushes it. On *this* dataset, C is not the overfitting knob — gamma is, and the
gamma sweep shows the failure C never produced. Written up as it came out rather
than smoothed over.

**The joint search scored lower on test than the single sweep.** `GridSearchCV`
chose `C=1, gamma=1` → test 0.9000, while the gamma sweep's best row was
`gamma=10` → test 0.9222. That is not the grid search underperforming. The sweep's
"best" was picked by reading the test column, which is exactly the mistake
`CLAUDE.md` tells reviewers of this repository to catch. The grid search chose on
cross-validated training data alone and never saw the test set, so 0.9000 is the
honest number and 0.9222 is a number selected on the thing it is meant to
estimate. Keeping both in the README is the point.

**Scaling mattered more than expected** (`07_scaling_matters.png`). Multiplying one
feature by 1000 dropped test accuracy from 0.8667 to 0.7889 and pushed the support
vectors from 69 to 90. The unscaled boundary is a *flat horizontal line*: feature
2 dominates the Euclidean distance so completely that feature 1 stops existing.
A decision tree would not have noticed this at all — it splits one feature at a
time, and any monotone rescaling gives the identical tree (see
`trees_and_boosting/DecisionTreeDepth.py`). The RBF kernel is a distance, so it
notices immediately. This is the sharpest contrast between the two model families
covered in this repository.

## What I Learned

- The margin, not the boundary, is what the model optimises — and the support
  vectors are the entire trained model. Everything else can be thrown away
- `C` and `gamma` are not two dials on the same thing. `C` trades margin width
  against violations; `gamma` sets the *shape* the boundary is capable of taking.
  Which one overfits depends on the other, which is why they are tuned jointly
- Defaults that look like constants are not. `gamma='scale'` is derived from the
  data, so any experiment that changes the rows also changes the kernel — which
  cost 4.4 points of agreement before the cause was found
- The support-vector count is a free diagnostic. "All of them" means C is too
  small; a handful means the model is resting on very little data
- An RBF SVM without feature scaling is a distance computed in the wrong units,
  and it fails quietly — a 7.8-point accuracy drop with no error and no warning

## What Was Deliberately Left Out

- **No `SVR`.** Regression with an ε-insensitive tube is a different picture and
  would have doubled the script for a second idea
- **No polynomial or sigmoid kernel.** Linear vs RBF carries the linear/non-linear
  contrast; adding kernels adds panels, not understanding
- **No real dataset.** Deliberate, as explained at the top — but it does mean this
  script says nothing about how an SVM scales. `SVC` is roughly O(n²)–O(n³) in the
  number of samples, which is the practical reason it lost ground to boosting on
  large tabular data. 300 points hide that completely
- **No multi-class.** Binary only; `SVC`'s one-vs-one strategy is plumbing, not a
  concept
